# StoryGenerate · 故事套路能力整合修改说明

> 2026-10-10 · 基于分支 `codex/storycraft-character-ending-v2`

---

## 一、修改目标

将旧版 LangGraph 的故事套路能力（10 类题材赛道、5 套角色配方、节拍规则）整合入新版 StoryWorkflow 创作流程，实现：

- 用户可**显式选择或自动匹配**不同的故事套路（Story Mode + Genre + Recipe + Template）
- 不同套路在人物关系、冲突机制、剧情发展、节奏和结局方面产生**实质差异**
- 保留新版创作优先、Plan 审批、ApprovedPlanSnapshot 冻结、Strong Writer 一次成稿的主流程

## 二、现状审计结论

| 能力 | 旧版 LangGraph | 新版 StoryWorkflow | 差距 |
|---|---|---|---|
| 10 类体裁 (G01-G10) | ✅ `s1_topic` 选题 | ❌ `genre` 字段存在但不注入 Plan | 体裁矩阵未进入 Plan prompt |
| 5 套配方 (R1-R5) | ✅ `s1_topic` 设置 `recipe_id`，`cast_design` 使用槽位 | ❌ `CreationPreferences` 无 `recipe_id` 字段 | **配方从未进入新版生成链路** |
| Mode 自动识别 | ✅ 规则匹配 | ⚠️ 仅 3 个关键词 → general | 大部分体裁落入 general |
| Template 解析 | ❌ 旧版不使用模板 | ✅ `StoryTemplateResolver` + mode 兼容 | 无 recipe-template 交叉校验 |
| 节拍表 | ✅ 通用 S1-S6 | ✅ 相同通用节拍 | 未按故事类型区分 |
| 策略统一解析 | ❌ 不存在 | ❌ 不存在 | **完全缺失** — 本修改核心填补 |

## 四、核心调用链

```
用户输入 → StoryStrategyResolver.resolve()
  ↓
  ├─ story_mode: explicit → genre-derived → "general"
  ├─ genre: explicit → keyword-match(idea) → best audio-fit
  ├─ recipe_id: explicit → genre-derived → None
  └─ 校验: recipe-mode 兼容性 → 冲突时显式报错
  ↓
ResolvedStoryStrategy (frozen snapshot)
  ↓
LLMPlanGenerator.generate() → PLAN_SYSTEM_V2 + strategy.plan_context()
  ↓
PlanPreview.strategy_snapshot (持久化)
  ↓
ApprovedPlanSnapshot (审批冻结，策略不可漂移)
  ↓
EpisodeCreativePacket.strategy_hints (Writer 可见)
  ↓
EPISODE_SYSTEM_V2 + strategy_hints → StoryDelivery
```

## 五、支持的组合

### 5 种配方 × 编剧机制

| ID | 名称 | 冲突机制 | 因果推进 | 结局策略 |
|---|---|---|---|---|
| R1 | 大女主升级流 | 升级式冲突：能力每升一层敌人升级 | 主角主动选择驱动 | 阶段性成就 + 更大世界暗示 |
| R2 | 萌宝团宠 | 反差式冲突：外界低估 vs 真实身份 | 误解 → 自然行动 → 真相揭示 | 温馨团聚 + 身份揭示 |
| R3 | 反差搞事业 | 认知差冲突：现代知识降维打击 | 信息差变现 | 事业成功 + 新世界立足 |
| R4 | 家庭反击 | 亲密关系权力反转 | 憋屈积累 → 觉醒 → 事实反击 | 关系重新定义 |
| R5 | 破镜重圆治愈 | 内心拉扯式冲突 | 偶然重逢 → 旧伤触发 → 渐进理解 | 和解与重新开始 |

### 4 种 Mode × 配方亲和度

| Mode | 兼容配方 | 通用性 |
|---|---|---|
| viral_drama | R1, R2, R3, R4 | 爆款公式 |
| general | R3, R4, R5 | 通用叙事 |
| mystery | 任意（优先 CausalProof） | 悬疑推理解谜 |
| serialized | R1, R2 | 连续剧连载 |

### 调用示例

```python
from drama_engine.workflow.schemas import CreationPreferences, StoryModeChoice

# 显式指定全部
prefs = CreationPreferences(
    story_mode=StoryModeChoice.VIRAL_DRAMA,
    genre="G01",        # 现实家庭冲突
    recipe_id="R4",     # 家庭反击
)

# 自动匹配
prefs = CreationPreferences(
    story_mode=StoryModeChoice.AUTO,
    genre="auto",
    # recipe_id will be auto-derived from genre
)
```

## 七、设计决策

1. **0-LLM 策略解析**：`StoryStrategyResolver` 完全是确定性的关键词匹配 + 查表，不增加 LLM 调用成本
2. **显式优先、自动填充**：用户指定的值永远不被覆盖；自动填充仅填补空缺
3. **冲突即报错**：不兼容组合抛出 `StrategyConflictError`，不静默覆盖（除非 mode=auto 时可自动调整）
4. **配方注入机制而非堆规则**：不像旧版把整个规则库 JSON 堆进 prompt，而是将配方翻译为精炼的创作指导（冲突机制、因果推进、结局策略、基调）
5. **不强制五槽位**：配方槽位在策略中可见但不强制，不同 Mode 按需使用
6. **不恢复旧版复杂校验**：保持新版一次成稿的轻量 Judge，不增加自动重写循环

## 八、尚未解决的问题

1. **节拍表仍未差异化**：`beat_sheet_for()` 对治愈、悬疑、爽剧返回相同的 S1-S6 结构。不同套路应该有不同的节奏模板
2. **真实模型对比测试**：当前测试使用 FixedPlanGenerator/FixedStoryExecutor mock，未用真实模型验证不同配方对生成质量的实际影响
3. **配方可在 Plan prompt 中更结构化**：当前策略以自由文本注入 system prompt，未来可考虑结构化 schema 让模型严格遵循
4. **Genre 自动匹配的精准度**：关键词匹配是快速但粗略的方案，对边缘 case 可能匹配不准

## 九、下一步建议

1. 为不同 Recipe 设计差异化的节拍模板（如 R5 治愈不应强制 S6 强钩子）
2. 用真实模型运行对照测试：相同创意 × 不同配方，保存 Plan 和 Delivery 对比
3. 在前端暴露 `recipe_id` 选择器，让用户能显式挑选故事配方
4. 收集真实用户数据，优化自动匹配规则
