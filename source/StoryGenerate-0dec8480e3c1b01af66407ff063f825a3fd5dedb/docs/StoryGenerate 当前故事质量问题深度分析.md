# StoryGenerate 当前故事质量问题深度分析

日期：2026-10-09
分析基线：`review/storycraft-prompts-v2-20261009@af1c8d1` 及其父分支真实产物
分析原则：人工编辑稿不作为模型原始生成成功证据。

## 1. 结论摘要

当前引擎已经具备可靠的审批、版本、结构校验和演绎合同，但“能交付合法 JSON”与
“第一次就写出好故事”之间仍有明显距离。StoryCraft v2 的方向正确，尤其补足了人物
选择、代价、可听线索和广播剧意识；主要剩余问题并非继续增加通用写作训令，而是：

1. 获批 Plan 的字段粒度仍偏粗，`major_beats: list[str]` 无法显式区分触发、依据、选择、
   代价和后果，模型只能从自然语言猜测场景因果。
2. 正文节点此前直接接收大纲整包，缺少确定性的逐场任务、人物知情范围、字数分配和
   声音时间预留，导致模型一边重新规划、一边写作、一边满足 Schema。
3. 角色 Profile 在固定 12 例中仍是“目标：推动故事中的选择”，无法支撑人物语言辨识度。
   这是输入数据缺陷，不能只靠 Prompt 修复。
4. 时长控制只给整集总字数；失败后整集重写最多两次，容易破坏已经成立的对白、事实和
   重音，且显著增加 Token 与延迟。
5. 演绎标注逐场调用，且此前复用 Balanced `episode_writer` 路由；这对结构性标注任务成本偏高。
6. Provider 已有调用历史，但估算 Token 与供应商 Usage 未明确分开，失败调用也缺少统一归属，
   不能直接作为财务账本。

## 2. 提示词成熟度诊断

### 2.1 已经成熟的部分

`workflow/storycraft_prompts.py` 的 p1.4.1 已从“按大纲写故事”升级为真正的编剧指令：

- Plan 明确外部目标、内部顾虑、阻力、选择、代价与后果；
- mystery 要求公平线索，serialized 区分单集闭合与长期悬念；
- Episode 禁止便利证据、知识越权和对白朗读设定；
- Performance 限制泛滥的高强度情绪与整句重音；
- Judge 被收窄为大纲、连续性和分级三项必要交付核验，不承担文学重写。

这些规则职责清楚，互相没有明显冲突。继续单纯拉长四份 system prompt 的边际收益很低。

### 2.2 仍不能仅靠 Prompt 解决的部分

- `PlanContent` 仍用四段式字段和字符串 beat，Prompt 写得再专业也无法保证每个因果元素可由
  程序检查或稳定传给下一节点。
- 角色资料为空泛时，模型只能临时发明性格；相同角色在 Plan、正文和续写中容易漂移。
- 总字数要求没有转换成逐场预算，模型往往把篇幅留给开场说明，高潮和结局被压缩。
- JSON Schema 很大，模型会消耗注意力在字段完整性上。合理方向是把确定性信息先整理好，
  而不是要求模型在一次调用中重新推导所有约束。

## 3. 正式生成流程的结构性问题

| 问题 | 源码证据 | 影响 | 分类 |
|---|---|---|---|
| 大纲到正文缺少场景创作包 | 原 `ApprovedPlanLLMExecutor.execute` 只传整个 Plan、单集 outline、beat sheet、角色和总字数 | 写作节点重复策划，场景篇幅与任务不稳定 | 上下文组织 |
| 角色输入贫弱 | `tests/acceptance/real_create_matrix.py` 使用“角色1”和“推动故事中的选择” | 人物语气趋同，配角沦为递答案工具 | 输入数据 |
| 时长失败整集重写 | 原 executor `for attempt in range(3)` 每次重新请求完整 `DraftEpisode` | Token 放大、已成立内容漂移 | 执行流程 |
| 演绎逐场多次调用 | `LLMPerformanceAnnotator` 每场调用，失败最多修复两轮 | 长故事调用数高；网络失败面扩大 | 执行流程/成本 |
| Judge 是单一模型布尔判断 | `QualityDecision` 仅三个 bool | 可做底线门，不能证明文学质量 | 评价边界 |
| 文本时长是假设值 | `spoken_chars / 3.5` | 不能代表真实 TTS、停顿、语速和音效 | 产品测量 |
| Usage 可信度不明确 | 原 `openai_compat.py` 缺 Usage 时估算 input、output 填 0 | 财务上会把估算误当实耗或把未知误当零 | 计量 |

## 4. 真实作品级比较

### 4.1 完整篇原始草稿

`spy_demo_complete_draft.json` 的主要问题：

- 主角听到异常后用“太反常、必须马上核实、后果不堪设想”直接解释情绪，缺少行动选择。
- “金属打火机声 + 前天掉落的齿轮声”并不能推出老秦使用备用机发私报；线索与结论之间有
  跳跃，苏棠随后直接宣布“他才是内鬼”。
- 收网依赖主角临时给出假地点、苏棠已经布控、录音键、夺枪等连续便利安排，前文没有充分铺垫。
- 老秦从否认到持枪再到放下，阻力迅速消失，人物代价和结局可信度不足。

人工稿《雾港第三声》修复了这些问题：

- 将核心证据改成可听的坏钟第二声、杯盖声、带子日期、钥匙和签字，形成可复核证据链；
- 每条信息有获得路径，苏棠也明确提醒“不替谁编故事”；
- 救援方案来自老秦自己签过的封航通知，反派行为反过来成为主角行动条件；
- 结尾以第三声敲门回应开场两声钟，主题和声音意象完成闭合；
- 主角首先选择救人、随后留证，人物价值通过行动体现，而非台词宣告。

### 4.2 长篇开场原始草稿

`spy_demo_serialized_draft.json` 的主要问题：

- “老秦失踪七年”后本人持冲锋枪突然进门，缺少出现路径；
- 角色轮流声称对方是假身份，反转主要靠宣布，而非新证据改变旧证据的含义；
- 沈砚最后声称自己早已改装机器、发走密码本，是典型“我早已安排好”的便利解局；
- 本集五分钟内把三人都变成疑似替身并让主角成为最终赢家，过早消耗长篇悬念；
- 大量表演说明依赖眼神、表情和视觉动作，不完全适合纯音频。

人工稿《雾港失踪档案》前五分钟修复为：

- 邮戳、天气、去年才修好的汽笛等证据证明录音可能是今天制作，推理步骤可追踪；
- 老秦只以录音、门外声音和广播出现，既保持可听性，也不提前确认其生死；
- “第七码”、照片缺半、第二张名单形成分层悬念，本集只完成保住证据的局部目标；
- 沈砚明确拒绝把身世猜测当证据，角色理性通过选择表现；
- 苏棠知情但不立即揭底，为后续剧集保留可追踪的关系冲突。

## 5. 可前置解决的共性问题

1. 在 Plan 中要求每个重要 beat 至少包含“行动、依据、状态改变”；后续可考虑升级结构化
   `BeatCard`，但本轮不破坏现有合同。
2. 在正文前确定性生成 `EpisodeCreativePacket`，明确场景任务、必达 beat、逐场字数、角色欲望、
   知情范围、连续性事实和声音时间预算。
3. 建立独立的富角色质量集，不修改原 12 例发布矩阵，以免丢失历史可比性。
4. 正文只允许一次首次生成；纯时长错误最多替换一个场景，角色越权、事实冲突直接失败并记录，
   不用全文重写掩盖。
5. 文学评价留在线下盲评；线上仅保留 Schema、审批快照、角色、事实、分级、时长与演绎底线。

## 6. 模型能力与流程的边界

- Strong 模型适合 Plan：因果设计和多约束策划的收益通常高于成本差。
- Balanced 模型适合正文：需要中文表达与长结构输出；是否改用其他模型必须做同条件 A/B。
- Fast 模型可承担演绎标注和轻量交付核验，但必须验证结构输出稳定性。
- 网络超时、503、TLS EOF 是供应商可靠性问题；不得计入文学失败，也不得触发创意重写。
- 当前没有证据证明增加独立“文学 Judge”能提升首稿，因此不建议加入线上主链。

## 7. 本轮诊断后的风险口径

本轮代码可以降低重复策划和全文重写，但不能仅凭单元测试声称故事质量已提升。最终判断必须依赖：

- 同输入、同 Plan、同模型参数的正文 Prompt A/B；
- 相同用户请求开始的全链路 A/B；
- 未经人工修改的原始 Delivery；
- 至少两名盲评者的作品级评分；
- 与质量分同时展示的真实 Token、调用次数、时延和失败归因。
