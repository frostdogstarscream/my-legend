# StoryGenerate：创作优先、争取一次成稿与 Token 计费建议（2026-10-09）

> 目标：基于用户最新确认的技术路线，调整 StoryGenerate Phase 10 及 StoryCraft v2 后续工作重心。
> 决策：**创作优先，轻量核验，争取第一稿直接可用；Token 精准统计纳入下阶段 Codex 开发计划，本次仅设计，不实现计费。**
> 范围：正式 StoryWorkflowService / LLMPlanGenerator / ApprovedPlanLLMExecutor；不改前端、数据库、支付或 TTS。

## 1. 方向调整：把能力前置到故事生成过程

不要以“普通 Prompt → 文学 Judge 找问题 → 自动重写 → 再次 Judge”作为主力研发模式。反复重写成本高，可能破坏已成立剧情、角色性格与已审批 Plan；更严格的 Judge 不会自动使第一稿更好。

建议采用：

1. **明确输入：** 故事操作（create / continue / revise / remix）、受众、角色最新快照、角色关系、题材、模式、时长、内容边界、历史事实、模板版本。
2. **强策划：** 一次生成完整、可演的因果大纲。将人物外部目标/内部顾虑、关键选择及代价、可听线索、开局承诺与结局兑现体现在现有 PlanContent 结构中，用户必须确认；用户主动修订大纲不计为“失败返工”。
3. **生成前上下文装配：** 把已审批 Plan 转为清晰的当前集创作包：人物声线与动机、不可改变事实、场景目标、悬念账本、节拍与字数预算。这是准备生成输入，不改变已批准的大纲。首期可在应用层确定性组装，不一定再增一次模型调用。
4. **高质量创作：** 专业编剧级 system prompt + 已审批数据 + 各场景可演事件、角色话语风格、可听证据、明确节奏预算。争取**一次 DraftEpisode 生成成功**。可以增加合理的前置 Prompt 与上下文 Token，但要测量边际收益。
5. **演绎输出：** 在台词确定后再加语气、重音与角色发声标记；保证每句演绎标注不更改剧本正文。
6. **轻量交付检查：** 结构/schema、角色绑定、批准大纲的重大节点、不可变事实、分级、基本时长、逐句语气重音合法性。可以保留单次简短模型核验，但不扩展为创作 Judge 循环。
7. **少量异常修复：** 只在 JSON 不合法、时长越界或重大事实冲突等明确硬错误时有限且定向修复；不要默认多轮整集改写。无法安全修复则报告明确失败与可定位原因，供后续版本优化。

**补充：** 首轮成功不等于完全取消校验。结构与安全仍是交付底线。将内容优劣评价用于离线分析和提示词/模型迭代，而不是每个真实用户请求都插入“文学评分 → 全文重写”。

## 2. 优先优化的生成因素（按优先级）

| 优先级 | 事项 | 创作端的实际动作 | 衡量方式 |
|---|---|---|---|
| P0 | 角色输入质量 | 每个角色有明确欲望、关系、说话习惯、行动边界；摆脱“角色1/目标是推动故事”的空卡 | 人物辨识度和对话重复率 |
| P0 | Plan 完整度 | 每场含目标、行动、阻力、证据、代价、后果；连载区分单集结局与长期主线 | 人工判定因果缺口数量 |
| P0 | Episode 创作 Prompt | 内部安排场景字数、线索揭示和对白意图；一次完整输出 | 第一稿成稿率 |
| P1 | 时长前置预算 | 合理分配台词与旁白预算、场景数量及音效时间，而非生成结束才发现偏差 | 初稿时长范围命中率 |
| P1 | 模式化故事创作包 | mystery/serialized/general/viral_drama 使用不同构思策略而非单一万能套话 | 每个模式的盲评 |
| P1 | 台词自然度 | 人物利用潜台词、误解、追问与行动推进情节 | 试听反馈、人工评分 |
| P2 | 生成前场景卡 | 当一次模型无法处理复杂长篇时，可在 Plan 已确认后创建场景卡供 Writer 使用；仍保持每场或每集一次正文写作 | 首稿质量、增量调用成本 |

**控制创作 Prompt 复杂度：** 越长不一定越好。按模型实际遵循能力建立版本化 profile，对相同样本用 A/B 测试，比较第一稿质量与 Token 消耗。不要只通过增加长度追求“专业”。

## 3. 取消以返工为中心的考核，改为首稿指标

建议记录但不强制立即实现：

- **Draft 首次通过率** = 首次正文模型调用完成后，直接满足结构、获批角色、时长硬约束的集数 / 发起生成的集数。明确区分模型不可用、超时与作品内容不合格。
- **全流程首次通过率** = 第一稿与第一轮演绎标注即可交付的任务数 / 进入正式生成阶段的任务数。不含用户在大纲阶段主动提交的修订。
- **平均每部完整故事的有效 Token 成本**，以及 P50/P95 生成时延。
- **首稿文学接受率（离线）** = 未经 Codex/人工修改的原始故事被独立试听者判为可接受的占比。用于版本研究，不要求每次线上生成都启动昂贵文学 Judge。
- **重试归因**：JSON/schema 修复、长度修复、语义问题、提供方超时、HTTP 503/TLS EOF 各自独立统计，避免误将网络失败归咎于编剧能力。

建议小规模对照：基线 p1.3.0，候选 p1.5.0，**相同模型、参数、同一套角色数据、题材与 Plan**；首先比较第一稿、不使用人工润色，不把局部修复后的 READY 结果当首稿合格。

## 4. Token 用量统计：现状与关键缺口

### 4.1 已有基础

- 供应商适配器：llm/openai_compat.py 使用 chat/completions 返回的 usage.prompt_tokens、usage.completion_tokens 记录成功调用。
- provider.call_history 含 role、requested_model、actual_model、attempt、latency_ms，以及成功时的 input_tokens/output_tokens；异常尝试记录状态和延迟。
- contracts.py 中已有 TokenUsage 与 InMemoryTelemetry.summary()，可以按节点汇总。
- 验收脚本会记录本次调用历史和 Token 证据。

### 4.2 为什么当前不能直接用于财务结算

- input_tokens 缺少 usage 时会使用估算值，当前没有清晰标识 reported/estimated；output_tokens 缺少时填 0。**估算或 0 不能当成供应商确认的应付账单**。
- 需要检查多次尝试计数：模型传输重试、结构化 JSON 重问、剧本重试、演绎重音定向修复、Judge 调用均可能产生实际成本；不能只记录最终成功回答。
- 缺少模型单价表/生效时间、缓存用量、可选 reasoning token、人民币/美元汇率及定价版本。
- 缺少 request_id/job_id/故事/用户维度的**贯穿聚合**与持久化唯一记录，服务重启后仍要保留。
- 超时/断连时供应商可能已执行并计费，本地没有 Usage 时应标记待对账，不可凭空算 0。

### 4.3 Codex 推荐实现的单次调用账本

每次实际 API 调用（**包括重试和失败尝试**）记录至少以下字段：

| 类别 | 字段 | 说明 |
|---|---|---|
| 归属 | ledger_id, principal_id, request_id, job_id, story_id, plan_id, episode_id | 按用户、作品及任务聚合 |
| 节点 | stage, node, call_id, attempt, prompt_version, prompt_hash | 大纲、修订大纲、正文、演绎、轻量核验；支持追踪重试 |
| 模型 | provider, requested_model, actual_model, model_price_revision | 按真实使用模型和价格版本计费 |
| 用量 | input_tokens, output_tokens, cache_read_tokens, cache_write_tokens, reasoning_tokens | 缓存/推理字段由供应商支持时记录 |
| 可信度 | usage_source: reported/estimated/unavailable, provider_request_id | **实际出账以供应商 reported 为准**，不可把 estimated 当准确值 |
| 结果 | status, error_code, started_at, ended_at, latency_ms | 成功、超时、HTTP 503、取消等 |
| 成本 | currency, input_unit_price, output_unit_price, cached_unit_price, estimated_cost, reconciled_cost | 采用 Decimal 和版本化单价，区分估算与对账 |

注意：部分供应商将 reasoning_tokens 计入 output_tokens，计算价格时必须按其文档的实际口径，**不要重复加总**。缓存读写、价格每百万 Token 或其他计价单位均按具体模型配置；不能写死统一价格。

### 4.4 两种账务口径必须分离

1. **实际供应商成本**：模型 API/网关向项目方产生的成本，按实际使用模型、用量、折扣和单价记录；供应商账单可能需要对账修正。
2. **面向用户的售卖价格**：套餐权益、按集数、时长、积分或按消耗量收费；是后续商业决策，不等于供应商 Token 成本。

如果以百万 Token 为价格单位，基础成本计算为：

供应商预估成本 = 普通输入 Token × 普通输入单价/1,000,000 + 普通输出 Token × 输出单价/1,000,000 + 缓存读/写等符合供应商口径的费用。

成本以 Decimal 计算，最后按财务规则舍入；价格必须包含币种、版本和生效日期。真实对账优先于本地估算。

### 4.5 汇总与运营指标

- **每次操作**：同一新建/续写/修改/二创请求从第一次大纲生成到最终交付的所有模型调用（包括用户反复修订大纲），提供子阶段用量明细。
- **每部故事/每集**：按 StoryVersion / Episode 聚合成本；对旧版与二创分别计量，不重复收费。
- **每个用户/日期/月**：生成次数、成功率、总 Token、平均供应商成本、余额/额度口径（商业定价待定）。
- **按模型与节点**：每模型请求占比、平均上下文长度、耗时、缓存命中、每成功集的 Token。
- **失败成本**：即便故事未 READY，重试和网关费用也需要可见；费用由谁承担属于产品策略，账本必须先记录真实成本。
- **计费幂等**：同一 provider call_id 与重放事件不能重复入账；结算以不可变账目及可追踪更正记录为依据。

### 4.6 Codex 具体实施任务（本轮只作为建议）

1. 设计 TokenCallLedger Pydantic + 持久化模型与 migration；不影响现有审批快照和 StoryVersion 不可变内容。
2. 在 Provider 边界统一埋点：每个请求及 attempt 都写 Call Ledger；SDK usage 的 reported/estimated/unavailable 明确区分；从服务节点传播 job_id/plan_id。
3. 从新 Plan 到 Episode Writer、Performance、Judge、JSON 重问统一累计；统计成功与失败，不因进程异常丢掉已确认用量。
4. 设计 VersionedModelPricing（币种、单位、价格日期、缓存/推理的特殊口径），用 Decimal 计算用量估值并留后续实际对账入口。
5. 新增 UsageSummary 查询：per_operation、per_story_version、per_user、per_model、per_node；同时输出已确认金额、估算金额、未知金额项数。
6. 单测覆盖：正常用量、多次调用、JSON 修复、超时但未知用量、503、缓存、reasoning 是否重复、模型切换、幂等去重、跨进程恢复、修改大纲多轮用量。
7. 提供一份真实模型小样本的使用成本报告，但绝不把缺失 usage 的金额虚构为真实供应商计费。

**实施顺序：P0 优先创作首稿质量、角色资料与时长前置预算；Token 用量账本设计为 P1 工程任务，宜在商业上线前完成。**

## 5. 对 PR #1 的口径调整

此次候选 Prompt 继续以策划与正文为主，保留演绎标注。Judge 限定为**少量确定或明显可验证的交付问题**，不充当文学二次编剧，不以文学分数驱动常规全文重写。

后续真正需要判断“提示词升级是否成功”，应优先检查**未经自动修复的首稿质量与 Token/耗时**，并把人工盲评限定为线下小样本对照研究。
