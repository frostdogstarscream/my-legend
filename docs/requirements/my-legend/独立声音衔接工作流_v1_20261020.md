# 独立声音衔接工作流 v1

## 范围与执行方式

本次新增 `sound_plan` 持久化生产阶段，将原来音频阶段内部的声音意图规划与审核移到独立模块。采用现有 PostgreSQL 任务调度、制品存储、调用账本和 Worker，不另建一套调度数据库。底层音频 LangGraph 和 StoryGenerate 保留。

新链路为：`story → sound_plan → audio`。声音准备阶段不调用 TTS 或音效生成接口。视觉继续暂停，本协议不用于视觉任务或已有音频的局部重制。

兼容请求继续使用原来的链路；新请求显式增加 `sound_workflow: "sound_bridge/1"`。新版 App 的“生成广播剧”和“从已有剧本制作广播剧”默认携带该字段。历史任务的阶段、制品和默认请求哈希保持不变，不自动迁移 unknown 任务。新请求与旧请求的哈希不同，不能使用同一幂等键切换链路。

## 阶段职责

1. 读取并验证同版本的 `StoryDelivery` 与 `RenderManifest`，原始剧本不改写。
2. 由模型对非朗读行分类：可听声音、纯声音控制、非声音动作。分类只返回固定 slot 的判断和理由。
3. 分类制品落盘后释放 Worker 租约，进入下一次调度；进程恢复时使用已保存的分类和调用结果。
4. 模型选择声音意图，程序编译执行操作，另一轮模型调用独立审查原文与操作的语义覆盖。
5. 程序构建配音清单、音效清单、控制清单及版本绑定信息，保存不可变制作包。
6. 音频阶段验证制作包后才预留并执行音频生成，消费既有编排，不再调用声音规划模型。

分类正常一次、规划一次、审核一次，共 3 次文本模型调用；音频模型调用在后续阶段另行记账。分类格式修复与声音方案修复共享此阶段的 `max_repairs_per_stage` 额度。调用结果未知仍停止并保留账本，不自动重发。

## 输入及 API

继续使用 `POST /api/v1/production-jobs`，在现有请求上增加：

```json
{
  "outputs": ["script", "audio"],
  "sound_workflow": "sound_bridge/1"
}
```

以上是新增字段示意，完整请求仍须包含合法的 source、idempotency_key 等原有字段。source 可以是 creative，也可以是已授权访问的冻结 delivery。能力查询 `GET /api/v1/production-capabilities` 新增 `sound_workflows`，并将 `sound_plan` 纳入 modules。未配置时提交返回 `MODULE_NOT_CONFIGURED`，不降级生成旧链路任务。

`GET /api/v1/production-jobs/{id}` 返回独立阶段状态；`GET /api/v1/production-jobs/{id}/artifacts` 列出制品；`GET /api/v1/production-jobs/{id}/artifacts/{sha256}` 返回已授权的原始制品。读取这些接口不会驱动任务执行或调用模型。

这是独立可调度阶段，不是另起端口的微服务。当前请求通过后会自动继续配音，没有新增“只运行声音准备”的公共输出类型。

## 输出契约

| 制品 | 内容 |
| --- | --- |
| SoundSourceClassification | 原文哈希、固定 slot 的声音分类和理由、模型响应与修复次数 |
| AudioArrangement | 保持原文、角色与顺序的可执行操作；时间关联由程序生成 |
| AudioArrangementReview | 独立语义审核、逐行和逐操作检查、方案哈希 |
| AudioArrangementEvidence | 意图选择、简化记录、编译政策、模型响应与修复记录 |
| SoundProductionPackage | 配音清单、音效清单、控制清单、固定音色及全部输入/审核哈希 |

`SoundProductionPackage` 的 JSON Schema 位于 `source/my-legend-production/src/my_legend_production/production/schemas/SoundProductionPackage.schema.json`。

配音清单保存完整朗读文本、原文定位、身份、固定音色及结构化表演字段；供应商 instructions 仍由已有音频适配器从这些原文表演字段组装。音效清单只含需要生成的 one_shot/background。控制清单独立保存停止、延续、程序淡入及非声音标记；控制不能当作音效素材提交。

制作包明确 `timing_basis=resolve_after_real_media`、`human_listening=pending`。未生成素材时不声称已获得真实时长或通过听感验收。

音频消费者会重建并比对制作包，核对剧本与清单哈希、角色音色、完整文本、表演字段、操作清单、审核与分类绑定。篡改、缺失、版本错误或未通过审核时，在任何音频提交前停止。

## 纯声音控制的修复

例如原文 `sfx: 脚步声停住，短暂的安静。`：

- 原文 kind、文本和行号仍然保留。
- 分类标记为 control_only 后，声音意图 Schema 禁止创建 sounds。
- 有活动背景时必须明确引用并停止或延续它；错误、重复或未知引用拒绝执行。
- 完全没有活动背景时保留零时长控制说明，不创建素材、不延长对白、不伪造静音配音。
- 当前有活动背景但未给控制目标时阻断，不猜测应该停止哪一个；复杂的“无相关背景但有其他背景”情况仍需明确规划。
- 如果原文包含新的可听声音，例如“脚步停住，钥匙落桌”，不能分类为纯控制。独立方案审核仍须检查遗漏；模型判断不是可靠性保证。

`CompoundSourceEvent` 新增可选 `sound_intent=control_only`，仅允许控制/标记操作；历史制品没有该字段时序列化不新增 null，保持旧方案哈希。内部编译可把纯控制标记降低为 action，但外层原文及实测时间轴仍保留原始 sfx 与出处。

## 失败与边界

- 分类多次无效：`SOUND_BRIDGE_CLASSIFICATION_FAILED`，保留问题报告，音频阶段等待上游处理。
- 方案审核失败：沿用 `AUDIO_CHOICES_REPAIR_FAILED`，保存已完成分类及方案问题，不开始配音。
- 制作包缺失/不一致：`SOUND_BRIDGE_PACKAGE_REQUIRED` / `SOUND_BRIDGE_PACKAGE_INVALID`。
- 外部调用结果未知：沿用 `EXTERNAL_RESULT_UNKNOWN`。本次没有修改供应商网络重试、结果查询、原生 TTS unknown 的恢复逻辑；这些是后续独立工作。
- 音频后续失败时，声音准备制品已单独完成并保留；不能因此称整条生产链已完成。
