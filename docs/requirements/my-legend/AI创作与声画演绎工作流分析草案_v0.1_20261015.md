# 我的传说 AI 创作与声画演绎工作流分析草案

日期：2026-10-15  
版本：0.1  
依据：用户确认的最终产品方向、两份开发包的实际源码与产物、当前 uni-app 前端。  
用途：明确能力、缺口与接入职责，供后续需求和接口设计使用；尚未冻结首发范围、模型选型、部署方案和排期。

“我的传说”的最终目标是让用户提出创意，由 AI 创作故事和剧本，再由模型配合完成声音制作与视觉表演，形成可以预览、修改、保存和播放的作品。故事、声音、视觉共同使用同一版本的剧情事实和人物身份。

当前声音包已经具有逐句表演设计模型、TTS 和独立音效模型的调用实现；视觉包具有结构化输入、素材与规则编排、预览和视频导出的基础，但视觉表演方案的 AI 设计尚未接入当前子工作流。外层整合入口仍是本地媒体模式。后续工作的重点是补齐 AI 视觉设计、建立正式的生产结果交接，并由业务服务管理制作任务与版本。

## 1 产品目标与制作职责

| 环节 | AI 承担的工作 | 程序和制作工具承担的工作 | 业务结果 |
| --- | --- | --- | --- |
| 故事与剧本 | 理解创作意图，创作故事，安排人物、场景、对白、旁白和行动，检查情节 | 保存版本，分配与校验稳定标识，检查引用与结构 | 可阅读内容及可制作的标准剧本 |
| 声音表演 | 根据人物、剧情和场景设计意图、情绪变化、语气、重音、停顿；生成配音与独立音效 | 参数适配、缓存、媒体处理、实测时长、精确次数和混音 | 分句素材、完整音频、制作记录 |
| 视觉表演 | 理解行动及对象，在素材和动作能力范围内设计人物表演与呈现方案 | 校验角色和动作，绑定素材，求值站位与运动，渲染画面 | 可执行表演计划、预览或视频 |
| 声画整合 | 必要时提出节奏调整建议 | 依据真实媒体时间计算统一时间轴，执行混音、字幕和视频导出 | 同版本的音频或有声视频作品 |
| 局部修改 | 理解作者的反馈，定位应修改的台词或表演要求 | 追踪依赖，只重做受影响结果，保留旧版本 | 可比较、可回退的新版本 |

LangGraph 用于编排这些任务、管理依赖和暂停恢复。一个业务环节不必对应一个新的 LangGraph 项目，也不要求每个节点都调用模型。已有声音和视觉子流程可以保持独立，由外层制作任务协调。

视觉模型参与表演设计，并不必然要求首版增加通用文生视频。AI 可以先根据剧本和已登记素材生成表演方案，再交给现有渲染链执行。人物图像、背景图像或视频片段的模型生成属于可扩展能力，不能据此自动扩大本次已确认范围。

## 2 两个开发包中的 AI 能力

| 能力 | 当前实现 | 还需补充或验证 |
| --- | --- | --- |
| 从创意生成故事和标准剧本 | 用户说明尚未完成；声音包支持向上游适配器取得剧本 | 待实际故事工作流交付后核对输入输出、审阅和版本；现有文件式上游接口不能代表已完成故事生成 |
| 逐句声音表演设计 | 声音包启用 `text_model` 后，逐句调用结构化文本模型；校验台词、角色、场景和上下文保持一致 | 自动选声、全剧节奏分析等能力不能由逐句设计直接推定，需要明确职责 |
| 项目与角色声音配置 | 代码汇总项目、角色、场景和逐句语境；音色来自 `role_voices` 等配置 | 当前配置音色不等于 AI 已能自动选角；可增加基于可用音色目录的候选推荐和试听 |
| TTS | 存在 Qwen Realtime 与 Qwen-Audio-TTS 适配器；包内有此前真实调用记录 | 实际可用模型、音色和账号权限在接入时核对；部分模板使用的普通 Realtime 模型不会提交表演指令 |
| 独立音效 | 存在 `QianwenSFX` 模型调用实现；提示词可以由已有制作要求和程序模板构造 | 全剧音效需求提取、候选选择、精确次数和语义质量分别确认；模型请求成功不等于音效可用 |
| 音乐 | 现有任务支持既有音乐素材或组合配方 | 当前源码没有完成音乐模型生成链，不将其列为已具备 |
| AI 视觉导演 | 当前 `visual_workflow` 未见与表演方案生成相连的文本或多模态模型调用 | 需增加“剧本和素材能力 → 结构化视觉表演方案”的模型步骤与校验 |
| 人物和背景实时生成 | 当前演绎读取已登记人物图集和背景 | 需要独立的生成、选择、登记、版本与一致性流程；包内现有图片不证明具备运行时自动生成 |
| 视频输出 | 整合层使用已有画面求值代码及渲染工具导出 MP4 | 当前输出依赖本地音频、特定手绘模板与工具链，尚非完整在线 AI 制作入口 |

声音侧“项目、角色、场景、逐句四层语境”中，项目要求、角色信息、音色及场景配置主要来自输入与配置；现有模型调用重点是逐句声音表演设计。`visual_semantics` 字段当前从原行动事件提取，不能据字段名称认定已经有 AI 视觉导演。

视觉包还包含既有小说转舞台剧的模型调用和旧业务 API。这些代码没有接入当前视觉子工作流的表演规划路径，也不能替代用户正在建设的故事剧本工作流。

依据：声音包 `performance.py`、`adapters.py`、`content.py`、`visual.py`；视觉包 `visual_workflow/graph.py`、`input_pipeline.py`、`planner.py`、`source_adapter.py`。

## 3 目标生产流程

用户选择角色、题材、风格和目标时长，输入灵感后，系统建立一项制作任务。用户可以在同一作品中持续修改，底层每次制作记录明确的输入版本。

| 阶段 | 输入 | 处理与依赖 | 输出 |
| --- | --- | --- | --- |
| 创作任务 | 用户需求、已选角色及目标 | AI 创作故事，再整理或生成标准剧本；处理内容问题 | 故事正文、标准剧本及问题记录 |
| 剧本基线 | 当前剧本 | 校验人物、场景、事件和制作边界，确定本次使用版本 | 固定的剧本版本及事件关系 |
| 声音准备 | 固定剧本、可用声音 | 配置或推荐角色声音；AI 逐句设计表演；整理音效需求 | 声音制作稿和调用任务 |
| 视觉准备 | 固定剧本、素材与动作能力 | AI 设计视觉表演；检查素材不足和动作能力；生成规则编译器能接收的输入 | 视觉方案和无声预览草案 |
| 媒体制作 | 两条准备支线的有效结果 | 配音、音效及选定的视觉素材制作可以按依赖并行 | 素材、实测信息、版本记录 |
| 联合编排 | 声音素材和视觉计划 | 回填实测时间，处理并行声音、动作锚点、字幕和转场 | 联合时间轴与预览 |
| 成品交付 | 当前预览、修改或确认结果 | 完成约定的技术、内容和效果验收，冻结所用版本 | 音频或有声视频、字幕与媒体清单 |

时间轴草案在固定剧本后建立，先描述先后、并行和关键动作关系。取得配音和动作的真实长度后，再计算可执行时间。视觉方案可以先准备，最终同步要等待真实媒体数据。

用户界面可以呈现一次“开始制作”，业务后台仍需保存各阶段任务。故事生成、声音制作和视觉制作分别成功，不自动等同于完整作品可交付。

## 4 故事工作流需要交付的内容

故事工作流尚未完成，现在可以先约定下游所需的信息类别，不提前要求上游服从某一套尚未冻结的总 Schema。

| 类别 | 下游需要的信息 | 原因 |
| --- | --- | --- |
| 作品与版本 | 作品标识、来源版本、修订关系、原始输入与当前成稿 | 定位制作基线及修改来源 |
| 人物 | 稳定角色标识、姓名、背景、关系、知情范围及当前状态 | 维持人物声音、画面身份与剧情一致 |
| 场景 | 稳定场景标识、地点和时间、环境、人物名单、开场在场状态 | 避免根据“谁说话”推断谁在场 |
| 事件 | 稳定事件标识、事件类型、台词或说明、说话人、行动者、对象和结果 | 分派声音与视觉任务 |
| 旁白 | 是否朗读、是否显示、叙述身份和视角、文本 | 区分旁白配音与行动字幕 |
| 声音需求 | 环境、拟音、音乐需求、关键次数及复用要求 | 支持独立音效制作和编排 |
| 制作边界 | 锁定事实、不可改台词、允许简化范围、目标时长及弹性 | 约束下游模型的表演加工 |
| 未解决问题 | 缺失人物、模糊对象、冲突、影响生产的问题及处理状态 | 缺项不能直接进入付费批量制作 |

建议保留一份面向业务的标准剧本视图，再分别适配当前声音 `lingban.script/1` 和视觉 `visual_script/1.0`。两套现有输入都有限定字段，不能把新业务字段直接塞入原协议。

稳定标识、引用映射和版本关系由程序维护。模型生成的临时编号需要经过归一化与校验，修改或增删事件时应明确哪些标识保留、哪些新增、哪些失效。

声音源码的内容修订会派生带点号的来源版本，当前视觉标识格式只允许字母、数字、下划线和连字符。正式适配时需要明确外部版本与模块内部版本的对应关系，保留原值和来源，避免直接拼接后被另一侧拒绝。

## 5 声音工作流的接入方式

现有声音 Pipeline 适合作为声音制作子流程保留，业务层调用其已有制作、状态、审阅及恢复入口。逐句缓存、调用预算、原始声音与处理结果分离、媒体哈希检查继续保留。

AI 接收已确认的台词、相关人物、场景和上下文，设计表演信息。TTS 收到朗读文字和所选模型支持的控制字段。动作说明、音效提示及制作备注保持独立。

需要区分三种修改：作者改台词，声音设计改变，最终混音参数改变。它们影响的缓存与派生结果不同。主动要求“再试一个版本”应形成新的候选，网络超时后的“重试”应先判断原请求是否已有结果，避免把恢复误当新创作。

当前默认每修订 8 次文本调用是样例预算配置，不适合作为任意长度作品的固定上限。实际任务需根据台词数量、允许修正次数和既有缓存制定预算；工作流调用计数与用户额度、金额账本分别管理。

声音子流程至少需要向业务层交付：所用剧本版本、声音配置版本、分句结果、素材引用与哈希、实测时长、混音、字幕、时间轴、失败及未确认项、审阅状态。业务层将文件结果登记为可访问的媒体资源，不把开发机绝对路径作为 App 接口。

## 6 AI 视觉导演与现有渲染链

视觉侧最需要补齐的是表演方案的 AI 设计。建议将这一环节放在现有规则编译器之前，其输入包含固定剧本、角色和场景状态，以及当前实际可用的素材和动作目录。

AI 输出应是可校验的表演方案：哪个事件由谁表演、针对谁、选择什么素材、执行何种支持的动作、与哪句台词或哪个声音事件关联，以及素材不满足时的差异。当前编译器不支持的镜头、表情或复杂动作应记录为能力缺口。

程序把方案适配为现有视觉输入，再校验人物、事件覆盖、动作能力、站位占用和素材版本，交给现有规则及渲染工具执行。精确坐标、帧采样、最终时间和输出文件路径由执行层控制。

例如，“角色甲推门进场，站定后低声质问；雨声持续”可以拆成：进场和留场状态、进场动作与关门声的关联、质问台词的声音表演、持续环境音层。AI 可以提出这样的方案，程序需要检查动作是否存在、人物是否已在场、声音事件是否可用，以及真实媒体能否满足安排。这个例子用于说明职责，不是本轮生成或验收结果。

当前手绘模板的动作范围为入场、退场、移动和等待，人物图集最多绑定 3 人。通用视觉输入还限制最多 2 个场景、全剧 100 条事件和 90 秒时长。要支持更长作品，可以评估分段制作与合成，但跨段人物状态、背景、声音连续性、字幕和版本必须另行实现与验收。

`generation_mode=automatic` 当前主要控制默认呈现和审核路径；默认外观由程序填入，不能作为 AI 已理解人物外观和表演的证据。

## 7 声画整合需要调整的职责

当前整合层只接受已存在的本地声音，要求文字模型和声音方视觉分支关闭，TTS 与 SFX 使用 `local`，模型预算为零。因此，直接放开预算或替换一个配置地址，不能完成在线 AI 制作接入。

建议把“生产”和“整合”之间的交接明确为同版本的制作结果。声音子流程完成对应版本的素材、混音和实测时间后，整合层消费这些结果；如需重新混音，应创建明确的新版本并记录原因。当前适配器会再次调用本地声音 Pipeline，后续需要确认如何沿用已确认结果及审核状态。

| 现有限制 | 面向完整 AI 链路的调整方向 |
| --- | --- |
| 声音与视觉事件必须一一对应 | 以共同剧情事件为依据，允许一个事件关联多个声音或视觉片段，也允许独立背景音层；所有派生片段可回溯来源 |
| 所有声音 placement 必须顺序且不重叠 | 分开主叙事事件、声音轨道和视觉动作，允许环境声、音乐与拟音并行 |
| 视觉 `narration` 在样例中可对应 SFX | 明确朗读旁白、行动说明字幕、纯声音事件各自的映射，不能按显示文本猜测是否朗读 |
| 仅按整段事件同步 | 先保留句级同步；需要词级动作或口型时，另接真实对齐数据及对应执行能力 |
| 子流程需要确认时，外层主要报未就绪 | 将等待输入、试听或确认作为可恢复的状态，向 App 提供相应操作 |
| 外层阶段缓存与子流程恢复分开 | 明确外层任务与子流程线程的映射，恢复时调用对应 continue 或 resume，验证崩溃后不会重复生成 |

这些调整属于接入设计与待实现范围。当前严格校验仍应保留，不能通过关闭版本、事件或时序检查来接受不匹配的数据。

## 8 业务后台与工作流的边界

uni-app 与业务后台通信，业务后台管理用户、作品、剧本版本、角色、制作任务、额度和媒体访问。工作流服务调用模型与制作工具，返回结构化状态和产物。模型凭据、解释器和工具路径由服务端配置管理。

| 边界 | 业务后台交给下游 | 下游返回 |
| --- | --- | --- |
| 剧本生成 | 创作需求、选定角色及相关历史 | 正文、标准剧本、问题、来源版本及模型记录 |
| 声音制作 | 固定剧本、声音映射、制作策略及预算 | 分句素材、混音、实测时间轴、状态及问题 |
| 视觉制作 | 固定剧本、素材能力、表演策略 | AI 表演方案、可执行计划、素材映射、缺口及预览 |
| 成品整合 | 同版本的声音结果与视觉计划 | 音频或视频、字幕、联合版本、审核和媒体清单 |

以上是业务职责清单，尚未定义正式 HTTP 路径或请求 Schema。当前前端已有 `/generation-tasks` 契约草案，不要求工作流直接模仿该接口；正式 API 在交接职责确认后统一设计。

任务模型需要区分“正在执行哪个阶段”与“当前执行或等待状态”。候选状态可覆盖排队、运行、等待输入、等待审核、部分失败、失败、取消请求和已取消；成品另外记录预览可用、审核状态和交付状态。取消应明确能停止哪些后续工作，以及已提交外部请求的处理方式，不能承诺撤回已发生的消耗。

当前声音包已有单制作目录的线程锁、SQLite 检查点与预算保护；这些能力不等同于多用户任务调度服务。业务任务的用户归属、队列、幂等、资源限制和媒体访问仍需服务层落实。

## 9 当前原型需要承接的用户体验

五个底栏与现有视觉风格可保留。后续重点集中在作品制作过程，而不是增加更多一级入口。

| 位置 | 面向 AI 创作链路的页面职责 |
| --- | --- |
| 创作 | 输入灵感，选择题材、角色、风格、目标时长和本次输出形式，查看制作限制与可用配置 |
| 作品详情 | 查看故事与剧本版本；在剧本、声音、演绎之间切换，明确当前结果对应哪一版 |
| 制作进度 | 显示剧本、表演设计、声音、视觉、整合等真实阶段；等待或失败时提供相应操作 |
| 试听与预览 | 收听完整混音、定位句子、选择声音候选、提出局部修改并比较版本 |
| 视频演绎 | 播放真实视频，以媒体播放位置更新字幕和人物；区分对白、朗读旁白与行动说明 |
| 角色 | 分开角色人设、剧中人物身份、声音配置和视觉素材，保存可复用的配置版本 |
| 我的 | 展示作品与制作任务、当前等待事项、实际额度记录和反馈入口 |

当前 `GenerationTask` 只有运行、成功和失败三种状态；`PerformanceMedia` 尚缺来源版本、事件标识和旁白类型。正式接入时需要补充对应信息。现有任务进度与本机阅读记录已经分别存在，不将它们描述为当前共用同一个字段。

作者可以看到简洁的开始制作、试听修改和保存作品；模型、预算、重试与同步细节由系统承接。现有声音工作流的正式交付要求人工审阅，首版由作者还是制作人员承担、哪些制作预览可以自动继续，需要在产品流程中确定，不能在服务化时自动改成已审核。

## 10 前一版需求草案的调整方向

| 原草案中的建议 | 根据本次确认的调整 |
| --- | --- |

| 自动视觉制作主要列为后续高级能力 | 将 AI 视觉表演设计列入目标链路；复杂视频模型生成与基础 AI 表演编排分开评估 |

## 11 建议验证顺序与完成条件

| 阶段 | 分析或后续实施目标 | 完成条件 |
| --- | --- | --- |
| 交接设计 | 明确标准剧本、声音、视觉、联合结果的交接，以及模型职责 | 每个输入、输出、版本、失败与恢复责任可定位；原有模块契约有明确适配方式 |
| 子流程验证 | 各自验证实际 AI 剧本、表演设计、配音、音效和 AI 视觉方案 | 有真实输入与输出、模型记录、有效素材及相应效果验收；缺少的能力如实记录 |
| 受限范围联合制作 | 可先选符合当前人物与时长能力的短篇，验证真正的 AI 声画生产 | 同一剧本版本贯穿；实际配音、视觉、字幕同步；局部修改后关联结果正确更新 |
| 业务服务接入 | 管理用户、任务、版本、额度和媒体 | 重复提交、断点恢复、失败、等待确认与版本隔离可验证 |
| uni-app 接入 | 替换模拟数据与进度，承接真实制作和播放 | 以实际后台结果验证创作、试听、修改和播放；目标终端分别验收 |

故事工作流未完成期间，可以用已确认的人工剧本检查下游交接和真实媒体制作。这样的验证应标记为下游联调，最终目标仍需用 AI 生成剧本完成端到端验收。

重点验收场景应包括：从创意完成作品；改一句台词；仅重做一句配音；替换背景音；人物跨事件持续留场；模型请求超时且结果未知；退出 App 后恢复查看任务；旧审核结果不能批准新媒体。制作时长、调用量和费用目标根据真实样本再测量，不由当前占位示例推算。

## 14 待确定的产品范围

后续接口定稿需要明确三个范围：首发是否同时交付故事、声音与演绎；视觉首期采用何种素材和动作能力，以及是否增加人物或背景的模型生成；声音与视觉成品的审阅由作者、制作人员还是双方分别承担。

当前分析采用“AI 参与视觉表演设计，复用现有素材与渲染基础”作为接入研究方向。最终产品仍以真实 AI 剧本、真实声音及相应视觉表演共同完成作品为目标。
